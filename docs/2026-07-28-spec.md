## Problem Statement

An engineer working in Claude Code wants to hand bounded work to a *different* coding-agent CLI —
for a genuinely independent second opinion, to keep a large diff review out of their own context
window, or to run something long in the background — and get a durable, inspectable result back.

Today only one such path exists (`ccodex`, Codex-only, PowerShell). Three problems follow:

1. **Only one advisor.** The engineer cannot route work to opencode or to a separate Claude Code
   instance, so they cannot pick the right advisor for the task or cross-check one against another.
2. **Building each wrapper separately triples the cost of the hard parts.** The expensive machinery
   is not the CLI invocation — it is durable job state, reliable cancellation, process containment,
   worktree isolation, and never hanging. Rebuilding that per backend guarantees drift in exactly
   the contracts callers depend on, and the engineer is a single maintainer.
3. **The naive unification makes things worse.** The three CLIs are not feature-parallel. A single
   uniform command surface that quietly means different things per backend would let the invoking
   agent compose calls that look valid and are not — and in the case of isolation flags, that is a
   safety boundary, not a convenience.

There is also a hard, verified obstacle. `opencode run` in headless mode **hangs forever, silently,
with zero output**, whenever any permission resolves to `ask` (study §5). Its only CLI-level escape
is a process-global `--auto` that opencode's own help labels `(dangerous!)`. A delegation tool whose
core promise is "this will not wedge your workflow" cannot be built on that path.

---

## Solution

One tool, one job model, three backends, three separate installed skills.

The engineer runs a backend-named command — `dcli-codex`, `dcli-opencode`, or `dcli-claude` — and gets the same
job lifecycle from all three: submit synchronously or in the background, poll or wait, read the
result, tail the logs, cancel, clean up, and diagnose. Implementation work runs in an isolated git
worktree the engineer inspects before applying. Reviews come back with a structured findings list.
Nothing is ever applied automatically.

Where the backends genuinely differ, the tool says so out loud rather than papering over it:

- Options that don't exist on a backend **hard-fail with exit 2 and name the alternative**, before
  any job is created. Never silently ignored, downgraded, or emulated.
- Options whose *meaning* differs get **backend-qualified names** — `dcli-codex --reasoning-effort`,
  `dcli-claude --reasoning-effort`, `dcli-opencode --variant` — instead of one flag with three meanings.
- Each backend gets **its own generated skill**, so the agent reading it sees exactly one coherent
  surface. Agents load skills by name, so three skills costs the agent nothing; generating them from
  one source costs the maintainer nothing either.

For opencode specifically, each job gets its **own** `opencode serve` process driven over HTTP. That
is what makes the no-hang promise real: a per-session permission ruleset (verified in study §7 to
defeat the §5 hang), endpoints to observe *and answer* pending permission and question requests, a
true `busy`/`idle`/`retry` status signal, and graceful session abort before any hard kill.

## User Stories

### Delegating work

1. As an engineer, I want to send a one-off question to another agent CLI and get its answer printed, so that I get a second opinion without leaving my session.
2. As an engineer, I want to pipe a long prompt in on stdin, so that I am not fighting command-line length limits or shell quoting.
3. As an engineer, I want to submit a long task to the background and get a job id immediately, so that I can keep working.
4. As an engineer, I want to choose which backend handles a task by running a differently-named command, so that the backend choice is visible in my shell history.
5. As an engineer, I want to pick the model for a job, so that I can trade cost against capability.
6. As an engineer, I want to set reasoning effort using the vocabulary my chosen backend actually accepts, so that I am not guessing which enum applies.
7. As an engineer, I want to tag jobs with a group and a label, so that I can fan out work and gather it later.
8. As an engineer, I want to cap a job's runtime, so that a wedged backend cannot consume my whole afternoon.

### Reviews

9. As an engineer, I want to review only a specific commit range, so that the review is scoped to the change I care about.
10. As an engineer, I want to review only specific paths, so that unrelated churn is excluded.
11. As an engineer, I want to review staged, working-tree, or untracked changes, so that I can get feedback before committing.
12. As an engineer, I want the tool to generate and embed the diff itself, so that the reviewer cannot review a moving target and does not need to be able to run git.
13. As an engineer, I want findings back as a structured list with severity, file, line, claim, evidence, and suggested fix, so that I can triage them mechanically instead of parsing prose.
14. As an engineer, I want a malformed findings block to be reported as malformed, so that a parse failure is never mistaken for a clean review.
15. As an engineer, I want review jobs to be incapable of modifying my working tree, so that asking for an opinion can never change my code.
16. As an engineer, I want to state the change's intent neutrally and have the reviewer told that intent is context and not evidence, so that I get an independent judgment rather than an endorsement.

### Background jobs

17. As an engineer, I want to check a job's state without waiting, so that I can decide whether to keep working.
18. As an engineer, I want to wait for a job with a timeout and a distinct exit code when the wait expires, so that my script can tell "still running" from "failed".
19. As an engineer, I want to wait for a whole group of jobs in one call, so that I never hand-roll a polling loop.
20. As an engineer, I want to read a finished job's result without waiting, so that collection is cheap.
21. As an engineer, I want to list my jobs newest first, optionally across repositories, so that I can find the one I forgot.
22. As an engineer, I want to tail a job's logs and events, so that I can see what it is doing right now.
23. As an engineer, I want a job whose worker died to be reported as failed rather than running forever, so that I am never waiting on a corpse.
24. As an engineer, I want to cancel a job and have the whole process tree actually die, so that nothing keeps burning tokens or holding locks.
25. As an engineer, I want cancellation to try the graceful route first where the backend supports it, so that partial work and logs survive when possible.

### Delegated implementation

26. As an engineer, I want a code change made in an isolated worktree, so that my working tree is untouched while the agent works.
27. As an engineer, I want to see the change's size before loading the whole diff, so that I can decide whether to read it in full.
28. As an engineer, I want to read the complete diff and decide myself whether to land it, so that nothing reaches my repository unreviewed.
29. As an engineer, I want to land the change under my own identity and message in one step, so that I am not amending commits by hand.
30. As an engineer, I want an apply conflict to leave my repository verifiably restored, so that a failed apply never leaves me mid-rebase.
31. As an engineer, I want to give follow-up feedback and have it continue the same conversation, so that I am not re-explaining context.
32. As an engineer, I want to apply only the newest accepted result in a chain of follow-ups, so that I do not land superseded work.

### Diagnosis and safety

33. As an engineer, I want a job that is blocked on a permission decision reported as blocked, not as a timeout, so that I fix the right thing.
34. As an engineer, I want quota, auth, permission, network, and timeout failures distinguished, so that I know whether retrying could possibly help.
35. As an engineer, I want the tool to refuse to retry failures that cannot succeed on retry, so that it never burns quota in a loop.
36. As an engineer, I want a credit-exhaustion failure not to be reported as an auth problem, so that I am not sent to re-authenticate a working login.
37. As an engineer, I want one command that tells me whether the backend, the wrapper, or my environment is broken, so that I stop guessing.
38. As an engineer, I want the raw backend events kept on disk, so that I can do forensics after the fact.
39. As an engineer, I want to know which backend versions are supported, and to be told clearly when mine is not, so that an upgrade does not fail mysteriously.
40. As an engineer, I want to see exactly which capabilities my installed backend has, so that I know what I can ask for.
41. As an engineer, I want aged job state deleted on request, so that this tool does not grow without bound.

### Agent-facing

42. As an invoking agent, I want an unsupported option rejected with a message naming the backend, the option, and the alternative, so that I can correct myself in one step.
43. As an invoking agent, I want that rejection to happen before a job is created, so that a mistake costs nothing.
44. As an invoking agent, I want one skill describing exactly one backend, so that I never assume a sibling backend's flag exists here.
45. As an invoking agent, I want a machine-readable capabilities report, so that I can check before composing a version-sensitive or extended call.
46. As an invoking agent, I want a lifecycle envelope with stable field names and exit codes, so that I react to structure instead of scraping human text.
47. As an invoking agent, I want raw backend output kept out of the parent's stdout, so that what I parse is exactly the result.
48. As an invoking agent, I want to be told never to apply automatically, so that a policy checkpoint cannot land unreviewed code.
49. As a maintainer, I want a project policy file setting when reviews and second opinions happen, minimum diff size, and a per-task call cap, so that delegation is bounded without re-prompting.
50. As a maintainer, I want a Claude Code worker to be unable to recursively delegate back into itself, so that a wrapped Claude session cannot fork-bomb my machine.

## Implementation Decisions

### Scope and shape

- **One repository, one job engine, three adapters, three shim commands, three generated skills**,
  plus an umbrella `dcli --backend <b>` for scripting. Rationale and the eight conditions that
  would reverse this: ADR-001 and its kill criteria.
- The shim name carries the backend; agents never repeat `--backend` on normal calls.
- Adapter implementation language may differ behind the boundary. **No adapter-specific conditional
  may appear in the shared engine** — that is the primary architectural invariant, and a violation
  is the ADR-001 R1 kill criterion.

### Backend strategy

- **opencode:** one wrapper-owned `opencode serve --port 0 --hostname 127.0.0.1` process **per job**,
  driven over HTTP (ADR-002). Not a shared daemon — lifetime, isolation, logs, and containment stay
  per job, and `opencode run` already starts an internal server anyway, so process count is
  unchanged. No CLI fallback: a second full backend would duplicate every hard subsystem while
  silently degrading the guarantee that motivated the choice.
- **Prompt execution is asynchronous.** Create the session with an explicit permission ruleset,
  connect SSE, submit via `prompt_async`, reconcile from SSE **plus** periodic session status, poll
  pending permissions and questions independently, and declare completion only from a terminal
  session state — never from SSE closure.
- **Codex:** `codex exec --json` with the prompt on stdin and `--output-last-message` for the result.
- **Claude Code:** `claude -p --output-format stream-json`, with `--session-id` assigned by the
  wrapper up front. Native `--bg`/`claude agents` is bypassed (ADR-005) because two job managers
  create ambiguous authority; recursion guards are mandatory.

### Contract surface

- **Core commands, identical on all three backends:** `run`, `submit`, `status`, `wait`, `read`,
  `list`, `resume`, `cancel`, `tail`, `diff`, `apply`, `debug`, `cleanup`, `doctor`, `capabilities`.
- **Core options:** `--repo`, `--prompt-file`, `--mode`, `--access`, `--hard-timeout-sec`, `--group`,
  `--label`, `--model`, `--json`. `--model` is only *syntactically* shared — model names do not
  transfer between backends.
- **Modes:** `review`, `brainstorm`, `test`, `implement`. **Access:** `read-only`, `workspace`.
  `review` is always read-only and rejects an override.
- **Exit codes and `status.json` fields are append-only.** Never rename or repurpose either; the
  installed skills, commands, and rules read them. Distinct `command_exit_code` and
  `backend_exit_code`; never a generic `exit_code`.
- **`state` is the terminal signal; `phase` is progress only.** A job may hold completion evidence
  while its process tree is still alive — observed live during this study, a Codex job sat in
  `finalizing` for 14+ minutes because a helper subprocess never exited. `status` surfaces a warning
  for that condition; callers must not key off `phase`.
- Backend-specific data lives **only** in a namespaced `backend_state` object, never as a new
  top-level field with backend-dependent meaning.
- Every job records a **capabilities snapshot** at creation, so a later backend upgrade cannot
  retroactively change how an old job is interpreted.

### The semantic-divergence rule (ADR-004)

> Share outcome-level contracts only where the wrapper can enforce them. Otherwise expose
> backend-native semantics under a backend-qualified name.

Feature differences are safe and declared as capabilities. Semantic differences are not unified.
Concretely, reasoning effort is **not** a shared flag: Codex has no effort flag at all (it is
`-c model_reasoning_effort=<none..ultra>`), Claude has `--effort low..max`, and opencode has an
unbounded provider-specific `--variant` string. Likewise isolation, approval semantics, resume,
cancellation, background ownership, structured output, and worktree/diff all differ structurally.

Emulating a missing feature for the sake of symmetry is banned. Wrapper-level implementation is
appropriate only when it creates a *real, enforceable* common invariant — wrapper-managed git
worktrees are the model case, and they belong in the shared engine precisely because the wrapper can
guarantee them regardless of native support.

### Isolation and applying

- Implementation runs in a **wrapper-managed detached git worktree**; the wrapper records
  `base_commit`, creates its own snapshot commit as `result_commit`, and `diff` compares the range.
- `apply` requires a clean main tree, refuses tracked dirt and in-progress rebase/am, and on conflict
  verifies restoration before reporting. **`apply` must never run automatically** at any policy
  checkpoint.
- opencode's native worktree and VCS endpoints are recorded as namespaced extensions for diagnostics
  only — they have their own identity and lifecycle and would weaken reproducibility and cleanup.

### Structured output

Not used natively, in either direction that currently works. opencode's `format: json_schema` is
**broken** in 1.18.7: it returned no parts and left the session's messages permanently unreadable
(study §8), with no safe in-session fallback. Codex's `--output-schema <FILE>` and Claude's
`--json-schema <inline>` both work but are structurally different mechanisms. The findings appendix
is therefore **wrapper-parsed from plain text**, uniformly, on all three backends.

### Never-hang engineering

Every blocking boundary has a finite default: worker startup sentinel, backend first-event watchdog,
server health-ready, job hard timeout, post-exit drain, HTTP connect/read, SSE idle, lock
acquisition, individual git operations, and the doctor smoke test. Child pipes are drained
**concurrently from launch** — the "write stdin then read stdout" ordering deadlocks against a full
OS pipe, which is exactly what a ~100 KB embedded review diff produces.

A pending permission or question while the session reports busy is classified **blocked**, not
timed out.

### Cancellation and containment

Escalation ladder, with the shared promise being the *outcome*: write the cancel request → adapter
graceful cancel (session abort where the backend has one) → bounded wait → dispose → bounded wait →
hard process-tree kill → verify. Record which rung was reached.

On Windows, containment is a Job Object with kill-on-close and breakaway disallowed, assigned by a
**small prebuilt native helper** before the backend can spawn descendants; wrapper death then lets
the kernel kill the tree. `taskkill` plus enumeration is the degraded fallback and is marked as such,
because it races newly-spawned descendants and cannot run at all if the wrapper is the thing that
died. On Unix, a new process group with SIGTERM→SIGKILL. Process identity is always
pid + creation time + image path, never a bare pid and never an image name.

### Language

**Plain JavaScript on Node.js, no build step**, plus that one native containment helper (ADR-003).
Under the HTTP-first architecture the workload is HTTP + SSE + NDJSON + schema validation, and
containment is a last-resort safety layer rather than the central mechanism. Type safety is recovered
with JSDoc + `checkJs`, explicit validators at protocol boundaries, and `AbortController` deadlines
on every HTTP call. Runner-up is pure Go; the deciding experiment is whether a Job Object can be
attached to the Bun-built opencode binary before it spawns descendants.

### Claude Code integration

Skills, commands, and the delegation rule are **generated** from one source plus adapter capability
manifests, and checked in. Generation tests fail the build when a public command is undocumented,
a capability is documented but undeclared, generated files are stale, installed files do not
byte-match the repo, or — most importantly — **one adapter's flag appears in another adapter's
skill**.

## Testing Decisions

### What a good test looks like here

Tests assert **external behavior at the seams**: process exit code, the exact bytes on stdout, and
the contents of on-disk job artifacts (`status.json`, `result.md`, `findings.json`,
`backend-events.jsonl`). They do not reach into internal functions or assert log wording. A test that
would still pass after the internals were rewritten, and would fail if the contract changed, is the
target.

### Seams

Four, deliberately few:

1. **The adapter interface.** The highest and most valuable seam. A deterministic **fake adapter**
   lets the entire job engine, every core command, the lifecycle, locking, reconciliation, and every
   exit code be tested with no backend installed and no tokens spent.
2. **A fake backend executable / fake HTTP server.** Below the adapter, for adapter-level tests:
   controlled event streams, malformed lines, oversized lines, unknown event types, hangs, pending
   permissions, pipe backpressure, surviving grandchildren, and death between spawn and sentinel.
   `opencode debug wait` is a ready-made indefinite-hang fixture.
3. **The real CLI**, opt-in, pinned per backend version, for live smoke only.
4. **Recorded golden fixtures** — argv, NDJSON/SSE/stream-json streams, OpenAPI responses, failure
   payloads — owned per adapter so updating one backend never rewrites another's goldens.

### What gets tested where

- **Core, against the fake adapter:** state root and job dir allocation; atomic `status.json` writes
  including the concurrent-reader window; lifecycle transitions; reconciliation of a dead worker to
  failed; locking under contention and PID reuse; every exit code; path normalization across spaces,
  non-ASCII, long paths, UNC, symlinks, junctions.
- **Contract suite, run once per adapter:** the same assertions all three must satisfy. This is what
  keeps the boundary honest and detects drift.
- **Adapter units, against fixtures:** event parsing and final-result selection; failure
  classification precedence — including the case that credit exhaustion arrives as HTTP 401 with a
  `CreditsError` body and must **not** classify as auth; capability probing; argv/request golden
  comparison.
- **Containment, live:** grandchildren die; wrapper death kills the tree; the degraded `taskkill`
  path is exercised and marks itself degraded; Unix process-group equivalents.
- **Worktrees, live git:** create, diff, apply, conflict, rollback, and verified restoration on the
  apply-conflict exit code.
- **Review:** findings validation, including that a malformed appendix yields null findings with
  prose preserved and is never reported as clean.
- **Generation:** no stale generated files; no cross-adapter flag leakage; installed files byte-match.
- **Never-hang:** a fixture that fills its stdout pipe before reading stdin must not deadlock; a
  blocked-on-permission fixture must be classified blocked, not timed out.

### Prior art

`ccodex` is the direct precedent and its approach carries over: plain assertion scripts run directly
and checked by **exit code**, with no test-runner framework dependency; a quick suite for iteration
that names what it skipped, and a full suite that must be green before anything is committed. Its
regression-guarded pitfalls list is reproduced as development-guide §1 — each item is a real bug
already paid for, and each needs a regression test here.

Reporting is **per suite**, so one broken adapter cannot mask the others.

## Out of Scope

- Reimplementing any backend's TUI, or any interactive UI at all.
- Managing providers, credentials, MCP servers, plugins, or backend configuration. The tool reads
  what it needs and points at the backend's own remediation command.
- Exposing any backend's database or internal state as this tool's own contract.
- Automatically applying implementation output, under any policy, ever.
- Letting review jobs modify a source tree.
- Automatic retry of quota, auth, permission, timeout, or malformed-result failures.
- A shared or long-lived backend server; hosting anything remotely reachable; sharing state between
  OS users.
- Using opencode's native worktree/VCS endpoints, Claude's native worktree or background agents, or
  Codex's native `review`/`apply` as production paths. All are recorded as namespaced extensions.
- Native schema-constrained output on any backend, for now.
- Supporting arbitrary backend versions without a compatibility check.
- Migrating existing `ccodex` job state. Old jobs age out under their own state root.
- ACP as an opencode transport.
- Any cross-backend model-name translation.

## Further Notes

**Sequencing.** Foundation and shared modules first, then adapters in the order
**opencode → codex → claude**. opencode goes first because it is the hardest adapter and the one
whose evidence shaped the architecture, so it validates the boundary while the boundary is still
cheap to change. Codex is deferred deliberately: `ccodex` works in production today, and porting it
before the shared engine is proven would risk a live regression for no gain. Claude is last because
it has the most unverified behavior and the only recursion hazard.

**One experiment gates the language choice.** Whether a Job Object can be attached to the Bun-built
opencode binary before it spawns descendants decides Node-plus-helper versus pure Go. It is cheap to
run and has the largest architectural consequence — do it in the containment ticket, before any
adapter work.

**Assumptions still open.** Study §11 lists sixteen unverified items and spec §19 adds ten. The ones
that gate real design decisions: permission-ruleset precedence and `deny` semantics; whether
`--port 0` reliably reports its bound port; basic-auth mechanics per endpoint; whether SSE can miss
events; whether `claude -p` can block on permissions the way opencode does; and whether
`--input-format stream-json` offers a control channel to answer them.

**Dogfooding is part of the process, not a nicety.** On `ccodex`, a scoped second-opinion review
after each phase repeatedly found real defects internal review missed — including an installer bug
that would have deleted all job state. Do it per phase, and triage every finding explicitly: adopt
with action, or reject with a stated reason.

**Naming is provisional.** The repository directory name is cheap to change; the CLI command names,
state-root directory name, and installed skill names are not, because they become part of the
contract other tooling reads.
